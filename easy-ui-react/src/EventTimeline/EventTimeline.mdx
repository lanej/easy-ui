# EventTimeline

A reusable selectable chronology. The caller owns ordering, interpretation, identifiers, and whether events belong to the same path. The timeline does not deduplicate events or infer physical histories.

## Usage

```tsx
import { EventTimeline } from "@easypost/easy-ui/EventTimeline";
```

## Examples

### Compact event ledger

Use `variant="ledger"` for a compact navigator beside a map and persistent
inspector. Each row starts with the semibold event type (`event.label`),
followed by its location and occurrence time on separate lines. Event types
and times are 12px; locations are 13px. Ordinary rows have a 64px minimum
height, with extra context and evidence increasing only the rows that need
them. Events without a location retain their event type and time. The
original `"timeline"` variant remains the default.

`renderTrailing` supplies a separate event assessment, such as a labeled risk
pill. It stays outside the event-selection button, remains independently
interactive, and is associated with the button's accessible description.
Event types, selection, and risk never share a severity color or inference.
The example below supplies its risk labels directly; missing assessment is
shown as **Not assessed**, never inferred to be low risk.

```tsx
<EventTimeline
  variant="ledger"
  size="compact"
  events={events}
  selectedId={selectedId}
  onSelectedIdChange={setSelectedId}
  renderTrailing={(event) => <EventRisk assessment={risks[event.id]} />}
/>
```

The selected background spans the row, including its trailing assessment.
Trailing assessments align with the event type at the top of the row. A
persistent inspector can show unassessed states while ordinary rows remain
free of repeated availability badges.
Ledger rows preserve caller order and do not draw an implicit connection
between adjacent events. Repeated locations and multiple delivery reports
remain separate records. `detailLabel` stays visible even in compact ledger
rows so supplied receipt or source distinctions are not lost. Detailed rows
also show the separately labeled receipt time; an event with no occurrence
label shows any available receipt time at every ledger size.

For a shared inspector, keep rich details in that inspector rather than
populating `renderDetails` on every row. In ledger rows, `metricsPlacement="inline"`
places an evidence strip across the full row beneath event type, location,
and time. Compact histograms or other supplied references keep their width
even beside a trailing risk badge. Metrics remain outside the native
selection button and inside the selected row; below metrics and interval
content retain their existing separate slots. Only return a metric strip for
events with evidence to show; rows without it keep their ordinary height.

### Explicit candidate relationships

Supply `connections` to draw a bounded graph gutter alongside the rows. Each
`EventTimelineConnection` names its own `id`, `fromEventId`, and `toEventId`;
optional `pathIds` and `label` preserve caller-owned context. Connections are
candidate relationships between observations, not a reconstructed physical
route. Shared path membership, matching locations, equal timestamps, and
adjacent rows never create a connection on their own.

```tsx
import {
  EventTimeline,
  type EventTimelineConnection,
} from "@easypost/easy-ui/EventTimeline";

const connections: EventTimelineConnection[] = [
  { id: "north", fromEventId: "shared", toEventId: "north-delivery" },
  { id: "east", fromEventId: "shared", toEventId: "east-delivery" },
];

<EventTimeline
  variant="ledger"
  events={events}
  connections={connections}
  selectedConnectionIds={["east"]}
/>;
```

A fork has one shared event and separate outgoing links. An independent origin
starts a new root; an unassigned delivery stays unconnected. Returning to a
place remains a distinct event with its own ID, and only explicit links decide
how that event relates to earlier observations. Multiple deliveries and
duplicate-looking observations are retained.

`selectedConnectionIds` emphasizes supplied relationships independently of
event selection. Rows keep the existing keyboard controls; the decorative
graph introduces no extra selection targets. Its native **candidate
relationships** disclosure lists every directed connection. Backward links,
self-links, and links with an endpoint outside the supplied event list receive
an explanation there. If more than four rails are required, the complete list
replaces the graph rather than hiding relationships or implying false joins.
Supplying `connections={[]}` also suppresses the ordinary chronology connector.

The example below has two candidate deliveries sharing earlier observations,
a separate origin-to-delivery history, and an unassigned delivery. Risk remains
an independent caller-supplied annotation.

### Event identity and independent metrics

The event's time, label, facility type, and location form its identity. Minimal presentation puts the event label, facility icon and type, location, and metric pills in one wrapping flow within the selected event surface. Compact and expanded measurements sit beneath event identity. Every pill contains both the metric label and its current value. The event-selection dot is independent of metric health: an arrival can have a healthy dwell time and an elevated exception rate at the same time.

The timeline frequently occupies **360–480px beside a map**. Facility text can wrap rather than being truncated to make room for statistics. The selected status dot retains clearance from the event text. Pills consistently display “Dwell time 6 h” and “Exception rate 2%”, with no repeated label outside the pill. Their colors convey their independent assessments; the full meaning remains available to assistive technology.

The three presentations below use identical synthetic observations at a **420px timeline width**:

- **Minimal:** the event label, facility icon and type, location, and both labeled metric pills share one flow. Individual pills wrap as space requires. No distributions.
- **Compact:** visible facility type and location, followed by one row per metric. Each pill contains its label and current value, with a concentration reference alongside when it fits.
- **Expanded:** the same event identity and labeled metric pills, with a larger distribution beneath each headline. The current value is not repeated in a second summary.

The reference shows one indicator for the current value. Percentile dots and tiny percentile labels are omitted. Distribution intensity describes the supplied reference, and only the policy interval containing the current value receives an assessment color. Other ranges remain visible in neutral color. Both the dwell-time and exception-rate examples have their own reference and assessment.

The example data is synthetic. The dwell reference contains completed durations; the exception reference contains percentage rates from comparable facility windows. Neither the component nor the example derives a percentage distribution from binary outcomes or treats a percentile as a health threshold.

### Compose metrics

```tsx
import { EventTimeline } from "@easypost/easy-ui/EventTimeline";
import { EventMetrics } from "@easypost/easy-ui/EventMetrics";

<EventTimeline
  events={events}
  selectedId={selectedId}
  onSelectedIdChange={setSelectedId}
  renderMetrics={(event) => (
    <EventMetrics
      variant="compact"
      metrics={metricsByEvent[event.id] ?? []}
      ariaLabel="Facility observations"
    />
  )}
/>;
```

For **minimal**, use `size="compact"`, `metricsPlacement="inline"`, and `renderMetrics` with `<EventMetrics variant="minimal" />`. The event label, visible facility type and location, and individual pills flow together. Rows without metrics use the same inline identity layout. The pills remain outside the native event-selection button, so metric controls retain their own actions.

`renderMetrics` is available on every event, including the final observation. `metricsPlacement` defaults to `"below"` for compact or expanded references. In the default timeline variant, `"inline"` includes content in the event's wrapping identity flow; ledger rows put inline content in the full-width evidence strip described above. Both placements keep metric content outside the event-selection button. `EventMetrics` accepts already formatted values and references, so durations, percentages, counts, and other measurements can share this composition without a domain dictionary in the timeline.

`locationIcon` accepts a caller-supplied icon. In the timeline variant, inline placement displays the facility type and location at every event size. In its default layout, compact event size keeps the icon and location while retaining the facility type for assistive technology; default and detailed sizes also display the facility type. Ledger rows place the icon beside the location and retain the facility type in the event's accessible description. Keep the metric presentation independent of the event's size.

### Selection and context

Supply `selectedId` and `onSelectedIdChange` to coordinate selection with an external map or details panel. A separate `onLocationSelect` callback exposes the location and event IDs; map pan and zoom remain application-owned.

Supply `relatedIds` to highlight events within a selected location, connection, or candidate path while keeping the complete timeline available. Selection and context highlighting are independent. An event's optional `detailLabel` adds concise caller-supplied context, such as a receipt time that distinguishes otherwise identical observations. It appears below the location in default and detailed rows; compact rows expose it as an accessible description.

Event time and received time are different fields; no implicit ordering or timestamp repair occurs. `renderTrailing` remains available for caller-owned side summaries. `renderMetrics` places measurements inline or below identity according to `metricsPlacement`. `renderDetails` supplies other content associated with an event. `renderInterval` supplies content associated with the interval following an event and is not rendered after the final event.

Keyboard navigation supports Up/Down and Home/End while retaining native button activation by Enter and Space.
