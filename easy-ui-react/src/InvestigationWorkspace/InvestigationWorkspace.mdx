# InvestigationWorkspace

An organism composing `EventTimeline`, `NetworkMap`, and a persistent detail panel. One controlled selection links observations, locations, candidate histories, and shared connections. Applications supply the records and their relationships; the component never chooses a true history or infers parcel identity.

## Usage

```tsx
import { InvestigationWorkspace } from "@easypost/easy-ui/InvestigationWorkspace";
```

For dense tracking investigations, use `variant="ledger"`: compact event-first observations, a quiet map, and one persistent inspector. Each row keeps its event type, location, and occurrence time visible. Explicit candidate relationships can add a branching gutter without treating time order as a travel route.

## Examples

### All-history investigation workbench

`InvestigationWorkbench` is an opt-in composition exported from
`@easypost/easy-ui/InvestigationWorkspace`. Existing workspace and ledger
presentations are unchanged. The workbench adds a compact header, history controls embedded in the event ledger, one Git-style branch graph at the far left of the shared
event-and-evidence ledger, map, and Details / Comparison /
Evidence inspector. It uses the native map, timeline, graph, pills and histogram
components rather than a separate prototype.

```tsx
import { InvestigationWorkbench } from "@easypost/easy-ui/InvestigationWorkspace";

<InvestigationWorkbench
  title="Parcel investigation"
  graph={graph}
  map={{ mapStyle, workerUrl }}
  predictions={predictions}
  deviations={deviations}
  assessments={assessments}
  renderConnectionMetrics={({ connection, fromEvent, toEvent }) => (
    <ApplicationInterval
      connection={connection}
      from={fromEvent}
      to={toEvent}
    />
  )}
  renderEvidence={renderApplicationEvidence}
  renderInspectorGraph={({ event, selectedEventIds }) =>
    event ? (
      <ApplicationDistribution event={event} selection={selectedEventIds} />
    ) : null
  }
  showHistoryLabels={false}
/>;
```

**One graph owns membership.** `InvestigationGraph` contains events, connections,
paths, and optional map locations/segments. Each path lists `connectionIds` and
optional `isolatedEventIds`, plus its label and stable literal paint color.
`normalizeInvestigationGraph` derives the event, connection and segment
memberships used by every view. It does not infer adjacency from row order,
shared locations or timestamps. Revisits retain their distinct event IDs;
independent roots, unassigned deliveries, forks and rejoins remain distinct.
Invalid IDs, references or mapped endpoints produce visible validation errors,
not silent repairs. `kind="recorded"` is caller-supplied, not inferred by the UI;
map line styling still follows each segment's measured/transfer/inferred/planned
provenance. Large branch graphs retain the relationship-list fallback. Focusing
a history does not remove other branches or invent joins.

**Focus is separate from selection.** Overview shows all observations and no
forecasts. Focused history emphasizes one history without filtering the ledger.
Every history, independent root and unassigned observation remains in the same
chronology, with a single continuous Git-style graph as the leftmost column.
Other map histories remain visible. The history chips sit within the event ledger
and retain accessible full names even when the default short labels are shown;
`showHistoryLabels` opt-in displays descriptive labels. The All histories
control returns to overview without discarding the current selection.
The Display menu contains unassigned-observation and risk-visibility switches.
`map.controls={false}` hides all built-in map controls.
Deviation analysis compares that history with an
explicitly chosen forecast. Selecting an event, revisit, location or connection
does not clear focus or prediction choices, and no such action requests a new
map camera. Location selection offers its distinct visits rather than choosing
one arbitrarily. `state` / `onStateChange` support controlled use;
`defaultState` supports initial uncontrolled state. The public
`InvestigationWorkbenchState`, `initialInvestigationWorkbenchState`, and
`reduceInvestigationWorkbench` expose the same state transitions.
All / A / B / C are the only history controls; there is no separate global mode switch.
Compare beside a prediction selects that reference and reveals the Comparison inspector,
including when that comparison is already active. Its button reads Comparing while active. Controlled mode
changes still wait for the application to accept the requested state. If the focused
history is removed, remaining map histories return to undimmed context without
choosing a replacement or discarding the unavailable selection.

**Selection is explicit and multi-event.** A history chip focuses and selects all
of its member observations without hiding other candidates. A plain event click
inspects that observation and selects one point; Shift-click selects a contiguous
range of supplied list entries, while Ctrl/Cmd-click adds or removes individual
entries. The ledger's Multi-select control enables the same additive toggles on
touch devices. A persistent count reports the selection; Done leaves that selection
intact and returns to single selection. Selection help explains mouse and keyboard gestures. In that mode, clicking a map location adds or removes all
observations at that location while preserving distinct revisits.
`state.selectedEventIds` stores the subset alongside
`state.selection` (the inspector's primary record). Selecting a history inspects that
history rather than retaining an observation from another history. Removing an inspected
observation or map location from a multi-selection moves inspection to a remaining
selected observation, or clears it when none remain. An initial default selection
also initializes its selected observations unless an explicit subset is supplied. Only caller-supplied map
segments associated with explicit connections between selected observations are
highlighted. Disconnected selected points stay disconnected. Clearing the subset
does not synthesize a path.

**Map expansion preserves the investigation.** Expand map uses the same mounted
map instance and changes only layout, not the selected observations, focused
history, forecast toggles, comparison or camera. Restore map or press Escape to
return. The optional `renderInspectorGraph` slot receives the current selection,
selected event IDs, and focused history ID and places application-owned charts
below the inspector's tabs in a collapsed Additional analysis disclosure.
Returning null omits the disclosure entirely. Comparison findings and supplied facts
appear before expandable Comparison evidence and sources, keeping conclusions visible.

**Evidence belongs to explicit connections.** `renderConnectionMetrics` receives
an incoming connection and both endpoints. It can compose compact
`DurationDistribution` histograms; `renderEvidence` expands their reference and
provenance in the persistent inspector. Two incoming edges remain independently
addressable. All explicit connections, including those between unassigned
observations or across histories, retain their incoming metrics and risk indicators
in the shared ledger. Only the explicit Unassigned observations display toggle
hides those rows; no other history is silently filtered. Risk annotations are supplied as `InvestigationAssessment` records
with event, connection or path targets, labels, tone, source and assessment time.
The Details inspector shows applicable path assessments while that history is
focused, event assessments for the selected observation, and connection assessments
for a selected mapped segment or observation's incident connections, always with
source and assessment time. Event types, path identity, selection and risk remain
separate. A controlled `state.selection: null` keeps the ledger unselected until
the application accepts a selection change.

**Predictions are not scans.** `InvestigationPrediction` supplies a history ID,
label, color, source, issuance time, disjoint geographic lines and optional dash
pattern. Each supplied line is split at antimeridian crossings without joining
separate lines. Each has an independent map visibility toggle; hiding the compared
prediction retains its findings and shows Hidden on map. Compare does not change
visibility, and there is no duplicate forecast selector in the inspector. Choices
survive leaving and returning to the history. Optional confidence must include a formatted value
and an explanation of what it measures. The UI derives neither probabilities
nor risk thresholds from histogram percentiles or map separation.
`InvestigationDeviation` supplies the comparison forecast, observation, optional
first-divergence observation, facts, source and assessment time. A first-divergence
annotation is shown only for one consistent supplied claim, combined with the
location label through the map's collision handling instead of a second marker.
The inspector's First supplied divergence action selects the exact observation;
disagreement is reported in text. Missing assessment means unavailable, never zero deviation.
`renderDeviationEvidence` provides application-owned comparison charts.

The examples are capped at 1100px, with a 230px map beside the ledger and a
scrollable inspector beneath it. Findings receive more vertical room; supplemental
charts stay collapsed until requested. Desktop validation uses 1100 × 820 and 960 × 820
viewports rather than an oversized desktop capture. Histograms stay in compact
connection-evidence rows; the inspector retains the full reference.

At narrow widths, Events / Map buttons switch
between the same mounted views. Widening with focus on Events or Map moves focus
to its retained panel. Resize handling never takes focus or view choice from a
sibling workbench. The inspector remains in normal page flow.
Inspector tabs support arrow keys and Home/End. Selection stays visible inside
the ledger's own scroll region without moving keyboard focus. Unassigned visits
are ordinary visible rows, not a closed secondary list. Caller-owned `actions`
remain visible and wrap in the header at all widths; only observation/history
counts are omitted below 1150px. The Data notes action demonstrates this in the
examples. Selection changes preserve map geometry/overlay references and the
camera. Theme changes preserve the map instance.

### Compact observations and candidate histories

```tsx
<InvestigationWorkspace
  variant="ledger"
  header={<ParcelSummary />}
  events={observations}
  locations={locations}
  segments={mapSegments}
  paths={candidateHistories}
  connections={[
    {
      id: "accepted-to-arrived",
      fromEventId: "accepted",
      toEventId: "arrived",
      pathIds: ["candidate-a", "candidate-b"],
      segmentId: "origin-to-hub",
      label: "Shared candidate connection",
    },
  ]}
  map={{ mapStyle, workerUrl }}
  selection={selection}
  onSelectionChange={setSelection}
  timeline={{
    renderTrailing: (event) => <EventAssessment event={event} />,
    metricsPlacement: "inline",
    renderMetrics: (event) => <CompactIntervalReference event={event} />,
  }}
  renderPathTrailing={(path) => <HistoryAssessment path={path} />}
  renderDetails={(context) => <InvestigationEvidence {...context} />}
/>
```

The ledger puts `event.label` first, followed by `event.locationLabel` and the occurrence time. Occurrence and receipt labels remain separate; supplied `detailLabel` can distinguish a revisit or an observation source. Selection is independent from event status and assessment. Optional `header` content joins the same surface above the compact history controls; the application owns its title, summary counts, and overall assessment.

`connections` contains explicit directed event relationships. `InvestigationConnection` extends `EventTimelineConnection` with an optional `segmentId` linking a relationship to caller-supplied map geometry. Matching times, locations, path memberships, or map endpoints never create event edges. A shared observation appears once and may have multiple `pathIds`; returning to a location requires a distinct event ID. Disjoint origins, separate delivery claims, and unassigned events remain separate. Rows retain caller order, including records after a delivery observation.

For existing workspaces with explicit connections, pass the replacement callback
through `timeline.renderConnectionMetrics`. `timeline.renderInterval` applies only
to the ordinary sequential presentation and is not called for explicit edges.

Supplying `connections`, including an empty array, replaces the timeline's ordinary sequential connector. Omitting it retains the existing chronological presentation. The graph draws only forward relationships in the supplied row order. Backward links, self-links, and endpoints outside a filtered view remain in the accessible relationship list with an explanation. More than four simultaneous rails use that complete list instead of compressing unrelated connections together. The graph is a candidate relationship view; it does not establish a physical parcel split or a confirmed route.

Without a candidate palette, the ledger defaults map connections to a subdued theme color. It uses `connectionStyle="subtle"` and hides ordinary labels until a location is selected. Caller-supplied segment colors, connection style, and `labelMinZoom` values remain authoritative. With explicit connections, selecting an event highlights only its incident event relationships and their supplied `segmentId` mappings; path selection highlights the candidate's supplied segments. Selection never moves the camera.

### Candidate colors and predicted paths

Give a candidate path an optional `color` to use the same identity color in its control, event relationship graph, and mapped connections:

```tsx
const candidateHistories = [
  {
    id: "a",
    label: "A",
    color: "#2563eb",
    segmentIds: ["shared", "a-transfer"],
  },
  {
    id: "b",
    label: "B",
    color: "#7c3aed",
    segmentIds: ["shared", "b-transfer"],
  },
];
```

Use literal MapLibre-compatible colors and supply the appropriate palette for the active theme. Colors identify caller-supplied membership and remain stable while selection changes emphasis. Shared mapped geometry displays parallel candidate strokes from one canonical segment; inferred and planned connections keep their dashes. A shared connection with only some candidate colors retains a muted stroke for each uncolored member. Shared graph links show their supplied candidate colors together, while shared event nodes remain neutral. An explicit `segment.color` takes precedence on the map. The graph derives its palette from `paths` by default; `timeline.pathColors` can override individual graph colors without changing the map or controls. Omit both palettes to retain the existing uncolored presentation.

With a candidate palette, location markers use the union of explicit `event.pathIds` across all supplied events at that `locationId`. A location with exactly one colored candidate uses that color; shared, unassigned, or uncolored membership stays neutral. This makes short connections discoverable through their endpoints without inferring a candidate from nearby geometry. Selecting one visit does not recolor the location or hide another visit's membership. Explicit location `color` remains authoritative.

`renderPathComparison(context)` provides optional controls or a legend immediately below the map. The workspace calls it only for an available focused path, including a path selection with a scoped `eventId`. Selecting an event, location, connection, or all histories removes this content. Return `null` for a candidate with no comparison. Its controls sit outside path and event selection buttons.

The application supplies predicted geometry through existing `map.overlays` and controls its visibility. Keep those overlays scoped to the same focused candidate; the workspace does not create, filter, or score forecasts. This example focuses A and offers two independently visible synthetic alternatives with an explicit as-of time and source. They add no observations to the timeline and compute no deviation or confidence score. Changing their visibility preserves the selected event and map camera.

### Assessment placement

| Scope                | Placement                                                     | Supplied content                                                           |
| -------------------- | ------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Investigation        | Caller-owned `header` above the history controls              | Overall assessment and its meaning                                         |
| Event                | `timeline.renderTrailing(event)` and `renderDetails(context)` | Brief labeled assessment; explanation and assessment time in the inspector |
| Candidate history    | `renderPathTrailing(path)` and the path inspector             | Candidate assessment, independent of selection                             |
| Interval or facility | Inspector or existing timeline metric slots                   | Only the measurements and reference data supplied by the application       |

Risk is not an event type or a graph lane color. A reported delivery can carry a high-risk assessment without changing its reported event type. Use text as well as tone, and distinguish an absent assessment from a low-risk result. Keep assessment time separate from occurrence and receipt time. The example's assessments are synthetic caller data; the workspace owns no thresholds, scoring, or relationship inference. Trailing content sits outside selection buttons so it may contain its own accessible actions.

The example uses sparse event badges: only supplied assessments appear in rows. Selecting an event without one explicitly shows **Unassessed** in the inspector. Candidate risk remains separately available through `renderPathTrailing`; a return visit alone does not create an assessment.

### Histograms and interval evidence

Use `timeline.renderMetrics` with `metricsPlacement="inline"` for a compact reference below a ledger row's identity, outside its selection button. Compose the existing `EventMetrics` and `DurationDistribution` components there. Return `null` when no measurement is supplied. The shared `renderDetails` inspector can add the full histogram, units, reference population, window, sample count, and exact-bin disclosure without expanding every row.

The branching example supplies two synthetic scan-interval distributions. The return visit's **7 h 05 m** interval follows its explicit Candidate A predecessor at 04:20, not the chronologically preceding Candidate B row at 07:56. Applications supply that association and the measurement; the workspace does not infer either. With multiple incoming relationships, label each reference's candidate or connection explicitly. Time between scans is not facility dwell. Preserve missing-data states and use actual supplied bins rather than constructing a distribution from a median or percentile.

On narrow containers the same observations, map, and selected event remain mounted behind Events / Map tabs. The ledger inspector follows the active view in normal page flow, so it cannot cover selected observations on short screens. Rich evidence expands from that persistent inspector.

### Controlled selection

```tsx
import {
  InvestigationWorkspace,
  type InvestigationSelection,
} from "@easypost/easy-ui/InvestigationWorkspace";

const [selection, setSelection] = useState<InvestigationSelection>(null);

<InvestigationWorkspace
  events={events}
  locations={locations}
  segments={segments}
  paths={candidatePaths}
  map={{ mapStyle, workerUrl }}
  selection={selection}
  onSelectionChange={setSelection}
  renderDetails={({ event, location, paths }) => (
    <ApplicationDetails event={event} location={location} paths={paths} />
  )}
/>;
```

Selection is `null`, `{type: "event", eventId}`, `{type: "location", locationId}`, `{type: "path", pathId}`, or `{type: "segment", segmentId}`. Location, path, and segment selections may include `eventId` for scoped stepping. Selecting a member event retains that scope; selecting an unrelated event switches to event selection. Callbacks request a change; only the caller updates the controlled value.

Events use the timeline's stable IDs, `locationId`, and optional `pathIds`. Candidate paths have stable `id`, `label`, optional `description` and `color`, and `segmentIds` referencing supplied map connections. No timestamps are sorted and no duplicate descriptions are collapsed. A path choice highlights supplied connections and related timeline rows. “Related only” filters that same event list while preserving caller order and the active scope. Event selection highlights its location and all supplied candidate memberships. Shared-connection selection reports how many candidate paths share the connection. The timeline highlights events across those paths, without asserting those events occurred on the selected connection. Events with identical occurrence labels expose supplied receipt times; these are also associated with the selection buttons for screen readers. The inspector retains the location/path/connection scope and position while stepping, and never duplicates the event list.

<Canvas of={Stories.LinkedSelection} />

Hovering the map previews its existing inspection card without changing the persistent panel. Changing the workspace selection dismisses map previews so they cannot obscure its navigation controls. Click, tap, Enter, and Space select. Timeline arrow keys, Home/End, and previous/next controls select events. The map's markers and the “Browse locations and connections” disclosure provide keyboard selection and remain usable if the engine fails. Unknown or invalid coordinates are left to the map's existing validation; unlocated events remain selectable. Removed selected records show an unavailable state instead of silently choosing another observation.

### Composition and layout

`map` accepts the existing `NetworkMap` options except its location/segment selection and data, which the workspace coordinates. Basemap, worker, camera policy, additional overlays, inspection renderers, legend, and exact data remain available. Selection does not automatically move the camera. The workspace omits duplicate map selection details, legend, and full raw-data tables by default. Controls sit over the map by default; pass `map.controlPlacement="toolbar"` to use a separate toolbar row. Individual location inspection is required, so clustered markers are not exposed by this composition.

`timeline` accepts the existing size and content slots, including `renderMetrics(event)` and `metricsPlacement`. Use `EventMetrics` there for compact or expanded measurements with the default `metricsPlacement: "below"`. For minimal presentation, use `metricsPlacement: "inline"`, `size: "compact"`, and `<EventMetrics variant="minimal" />`. The ordinary timeline shares a wrapping flow between identity and pills; the ledger places metrics in a full-width strip beneath its three identity lines, within the selected surface and outside its button. Rows without metrics keep their compact identity. `renderDetails(context)` adds caller-owned content below the selection summary; health assessments, distributions, facility summaries, and application actions are optional. Its context contains the selected event/location/path/segment, scoped events, all associated paths, and availability. Event time and received time remain separate.

The following example supplies a healthy dwell time and an elevated exception rate for the same event. Both metrics retain their own labeled current-value pill and concentration reference in the timeline; the inspector expands the references. Event dots remain neutral, and selecting another event or location still uses the same controlled selection behavior.

On wide containers, events sit beside the map and inspector. The ledger uses equal columns and a 225px map by default; its selected inspector follows immediately below the map. At 640px and below for the ledger, or 740px for the default workspace, Events / Map tabs switch between the same mounted views. Selection, detail state, and the map camera survive switching views and resizing. Narrowing keeps the focused event or map panel visible; widening moves focus from a disappearing tab to its panel. ### Map-free timeline and inspector

Import the inspector and selection helpers from the supported workspace entrypoint. No map, location geometry, or deep imports are needed for event-only records:

```tsx
import { EventTimeline } from "@easypost/easy-ui/EventTimeline";
import {
  InvestigationDetails,
  resolveSelection,
  selectEvent,
  type InvestigationSelection,
} from "@easypost/easy-ui/InvestigationWorkspace";

const [selection, setSelection] = useState<InvestigationSelection>(null);
const context = resolveSelection({ events }, selection);
const chooseEvent = (id: string) => setSelection(selectEvent(context, id));

<>
  <EventTimeline
    events={events}
    selectedId={context.event?.id ?? null}
    onSelectedIdChange={chooseEvent}
  />
  <InvestigationDetails
    context={context}
    chooseEvent={chooseEvent}
    clear={() => setSelection(null)}
    labels={{ empty: "Select an account event." }}
    renderDetails={({ event }) => <ApplicationDetails event={event} />}
  />
</>;
```

`resolveSelection(records, selection)` retains caller order and marks removed records unavailable. `InvestigationRecords` requires only `events`; `locations`, `segments`, `paths`, and explicit event `connections` are optional. Its returned `connections` contains the supplied relationships for the selected event, location, path, or mapped segment. Event selection uses incident endpoints; path selection uses explicit relationship membership; segment selection uses explicit `segmentId`. `selectEvent(context, id)` preserves an available scope for member events. Both helpers are pure; changes remain controlled by the application.

`InvestigationDetailsProps` exposes `context`, `chooseEvent(id)`, `clear()`, optional `renderDetails(context)`, optional partial `labels`, optional `isNarrow`, and `variant="default" | "compact"`. The compact variant heads the inspector with the selected event's location, then its event type, and omits the duplicate location fact. The ledger workspace selects it automatically. The inspector supplies previous/next boundaries and clear controls. The default labels match the workspace; `InvestigationDetailsLabels` describes the supported overrides. `InvestigationDetailsContext`, `InvestigationRecords`, `InvestigationPath`, `InvestigationConnection`, and `InvestigationSelection` are public types from the same entrypoint.

The standalone inspector observes its own container at the native 740px breakpoint. It retains metadata and navigation while rich content collapses behind Show details. Content stays mounted, and focus moves to the disclosure if narrowing hides the focused action. Widening reveals the same content. If Show details or Hide details had focus, focus returns to the persistent inspector region rather than the document body. Pass `isNarrow` only when a parent layout already owns this decision; `InvestigationWorkspace` does so internally. Compose the timeline and inspector in the application's layout; timeline arrow keys and Home/End remain native.
